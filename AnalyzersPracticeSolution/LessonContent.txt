Section 05 — Semantic Analysis

This is the major transition from "what does this code look like?" to "what does this code mean?" Roslyn distinguishes syntax structure from semantic meaning through compilations, semantic models, binding, symbols, and type information.

Section 07 — Operations and Higher-Level Code Analysis

This is where I would introduce Roslyn's operation model. It gives analyzers a representation based more on program semantics than the exact syntax used to express them.

Introduction to IOperation
Registering Operation Actions
Analyzing Assignments and References
Analyzing Invocations
Analyzing Unary and Binary Operations
Choosing Between Syntax, Symbols, and Operations

Your practical Boolean-literal analyzer belongs here.

By this point you would understand diagnostics, syntax, testing, semantics, symbols, and operations. So an exercise can legitimately ask you to detect:

isValid && false
isValid && true
isValid || false
isValid || true

without me essentially having to teach you the implementation while giving you the requirements.

And importantly, this remains analyzer only. We would diagnose your accidental secondFound && false; we would not write the automatic == false correction here.

Section 08 — Broader and Stateful Analysis

So far most exercises can inspect one thing independently. Now the analyzer learns to reason across a larger scope.

Roslyn's own samples distinguish these stateless analyzers from stateful analyzers that work across code blocks or compilations.

Syntax Tree Analysis
Semantic Model Analysis
Code Block Analysis
Compilation Analysis
Compilation Start and End Actions
Maintaining State Safely Across Analysis

This is an important difficulty jump and should come fairly late.

Section 09 — Configuration and Project Inputs

Analyzers eventually need to behave like actual development tools rather than hard-coded demonstrations.

Analyzer Configuration Fundamentals
Reading .editorconfig Options
Rule Severity Configuration
Using Additional Files
Building Rules from External Configuration
Configuration Defaults and Invalid Configuration

Current .NET analysis supports .editorconfig-based rule configuration, while Roslyn's analyzer infrastructure exposes additional non-source files through analyzer options.

This section could eventually produce useful personal analyzers where your coding rules are configurable rather than baked permanently into the implementation.

Section 10 — Production-Quality Analyzer Design

This is where the course transitions from "I know Roslyn analyzer APIs" to "I can make an analyzer I would actually trust in my projects."

Generated Code Analysis
Concurrent Analyzer Execution
Avoiding Unnecessary Analyzer Work
Reducing False Positives
Handling Incomplete and Erroneous Source Code
Selecting the Correct Analysis Scope
Stateless vs. Stateful Analyzer Design
Building and Testing a Realistic Multi-Rule Analyzer

This final section is especially relevant to your reason for learning analyzers in the first place: you want tooling that catches recurring attention-to-detail mistakes. An analyzer that produces false positives or behaves unpredictably would undermine that purpose, so correctness and restraint deserve explicit lessons.
